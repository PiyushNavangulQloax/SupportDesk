## Question 2: JWT (JSON Web Token) Concept & Statelessness
- **Concept:** JWTs transmit user claims as signed, self-contained JSON strings. The server does not store active session records in memory or database; it mathematically verifies the signature using `JWT_SECRET`.
- **Repository Implementation:** `src/utils/jwt.ts` (`signToken`, `verifyToken`).
- **Question:** Why is JWT-based authentication in SupportDesk described as "stateless", and what primary architectural benefit does this provide?
- **Correct Answer: (C)** The server does not maintain session state in memory or the database; any server instance with the `JWT_SECRET` can verify the token's signature, enabling horizontal scalability without session database lookups.
- **Why Other Options are Incorrect:**
  - *(A) is incorrect:* Storing tokens in PostgreSQL is stateful session management, defeating the primary purpose of JWTs.
  - *(B) is incorrect:* SupportDesk uses symmetric HMAC-SHA256 (`HS256`), not RSA, and the token is signed, not encrypted.
  - *(D) is incorrect:* JWTs cannot unilaterally regenerate themselves without contacting a refresh endpoint.

## Question 3: JWT Structure: Header, Payload, and Signature
- **Concept:** A JWT consists of three base64url-encoded parts separated by periods (`header.payload.signature`):
  1. *Header:* algorithm and token type (`{"alg": "HS256", "typ": "JWT"}`).
  2. *Payload:* user claims (`{ id, email, role, exp }`).
  3. *Signature:* cryptographic hash calculated over header and payload using the server's secret key.
- **Repository Implementation:** `src/utils/jwt.ts` enforces `algorithm: "HS256"`.
- **Question:** Which statement correctly describes the internal structure and security properties of a JSON Web Token?
- **Correct Answer: (A)** A JWT consists of three dot-separated base64url-encoded components: a Header specifying the algorithm, a Payload containing user claims, and a Signature created by hashing the header and payload with a secret key.
- **Why Other Options are Incorrect:**
  - *(B) is incorrect:* The payload is base64url-encoded, not encrypted; anyone who intercepts it can decode the JSON claims.
  - *(C) is incorrect:* The signature is generated by the server using `JWT_SECRET`, never by the client browser.
  - *(D) is incorrect:* A JWT has three components, not two.

## Question 4: Access Tokens and Token Expiration
- **Concept:** Access tokens must have finite lifetimes (`exp` claim) to mitigate the damage of token theft. Once issued, a stateless token cannot be unilaterally revoked without a blocklist; expiration limits the window of vulnerability.
- **Repository Implementation:** `src/config/env.ts` configures `JWT_EXPIRES_IN="1d"`.
- **Question:** Why must JWT access tokens always include an expiration (`exp`) claim, and what happens when an expired token is sent to the SupportDesk API?
- **Correct Answer: (D)** Expiration limits the window of opportunity if a token is intercepted; the `verifyToken` utility catches expired tokens and throws an `UnauthorizedError` resulting in HTTP `401 Unauthorized`.
- **Why Other Options are Incorrect:**
  - *(A) is incorrect:* Tokens without expiration remain valid indefinitely, creating an unacceptable security vulnerability.
  - *(B) is incorrect:* Expired tokens return `401 Unauthorized`, not `403 Forbidden`.
  - *(C) is incorrect:* The server does not silently auto-renew expired access tokens without a dedicated refresh exchange.

## Question 5: Password Hashing vs. Encryption
- **Concept:** **Hashing** is a one-way mathematical function; you cannot turn a hash back into the plaintext password. **Encryption** is a two-way function designed to be decrypted with a private key. Passwords must always be hashed, never encrypted.
- **Repository Implementation:** `src/utils/password.ts` uses `bcrypt.hash()` and `bcrypt.compare()`.
- **Question:** What is the critical difference between password hashing and password encryption, and why does SupportDesk use hashing for user credentials?
- **Correct Answer: (B)** Hashing is a one-way function that cannot be mathematically reversed, ensuring that even if the database is leaked, raw user passwords cannot be recovered.
- **Why Other Options are Incorrect:**
  - *(A) is incorrect:* Encryption is two-way and can be decrypted if the key is compromised.
  - *(C) is incorrect:* Hashing is not designed for fast decryption; passwords should never be decrypted.
  - *(D) is incorrect:* Passwords should never be stored in reversible format in databases.

## Question 6: bcrypt Algorithm & Salt Work Factor
- **Concept:** Bcrypt incorporates a unique random salt into every hash to defeat rainbow tables, and has an adjustable work factor (number of hashing rounds, e.g. 12) that forces deliberate CPU computation, slowing brute-force cracking attempts.
- **Repository Implementation:** `src/utils/password.ts`: `const SALT_ROUNDS = 12;`.
- **Question:** How does bcrypt defend against rainbow-table attacks and brute-force password cracking in the SupportDesk database?
- **Correct Answer: (C)** Bcrypt automatically generates a unique salt per password (defeating rainbow tables) and uses a configurable work factor (12 rounds) to deliberately slow down computation, making dictionary attacks infeasible.
- **Why Other Options are Incorrect:**
  - *(A) is incorrect:* Salt does not encrypt the database table; it provides random input to individual password hashes.
  - *(B) is incorrect:* Bcrypt does not require contacting external authentication servers.
  - *(D) is incorrect:* Work factor increases hashing difficulty, not encryption key length.

## Question 7: Authentication Middleware in Express
- **Concept:** Middleware functions in Express intercept the HTTP request lifecycle. The `authenticate` middleware inspects the `Authorization` header, extracts the Bearer token, validates it, and attaches the payload to `req.user` before calling `next()`.
- **Repository Implementation:** `src/middleware/auth.middleware.ts` (`export function authenticate(req, res, next)`).
- **Question:** What is the primary role of the `authenticate` middleware in `src/middleware/auth.middleware.ts`?
- **Correct Answer: (A)** It intercepts incoming HTTP requests, extracts and verifies the Bearer JWT token from the Authorization header, attaches the decoded payload to `req.user`, and calls `next()` to proceed to route handlers.
- **Why Other Options are Incorrect:**
  - *(B) is incorrect:* The middleware does not check database tables; it verifies the JWT signature statelessly.
  - *(C) is incorrect:* It does not handle request body schema validation; that is handled by `validateRequest(schema)`.
  - *(D) is incorrect:* It halts execution with `401` on invalid tokens instead of passing unauthenticated requests to controllers.

- **Question:** When should an API return HTTP `401 Unauthorized` versus HTTP `403 Forbidden`?

- **Why Other Options are Incorrect:**

## Question 15: Runtime Request Validation with Zod

- **Repository Implementation:** `src/schemas/ticket.schema.ts`, `src/schemas/auth.schema.ts`, `src/schemas/comment.schema.ts`.
- **Question:** Why does SupportDesk use Zod schemas for request validation when TypeScript types are already declared?
- **Correct Answer: (A)** TypeScript types are erased during compilation and cannot validate data at runtime; Zod parses and validates untrusted HTTP input at runtime, guaranteeing type safety and rejecting malformed payloads.
- **Why Other Options are Incorrect:**
  - *(B) is incorrect:* Zod does not replace database migrations or generate SQL schemas.
  - *(C) is incorrect:* Zod is not an encryption library for hashing passwords.
  - *(D) is incorrect:* TypeScript alone cannot intercept runtime HTTP requests without a validation library.

## Question 18: Ticket Ownership Isolation & Anti-Enumeration (IDOR)

- **Why Other Options are Incorrect:**

  - *(B) is incorrect:* It is not a database bug; it is an intentional security design decision.
